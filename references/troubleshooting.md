# 排错对照

按“症状 → 常见原因 → 处理”组织。改配置前先备份，验证用最小请求，不要靠猜。

| 症状 | 常见原因 | 处理 |
| --- | --- | --- |
| 启动即报配置解析错误 | TOML 写坏、值没加引号 | 用 `codex features list` 之类的只读命令确认配置能加载；`-c` 的值按 TOML 解析，字符串必须带引号 |
| 401 / invalid api key | key 来源错误、取钥脚本输出为空或有换行垃圾 | 单独运行取钥脚本确认只输出 key；检查文件权限与 `auth.command` 路径 |
| 400 / model is not supported | 模型 slug 与提供方不一致（多了或少了命名空间前缀） | 用提供方文档里的准确 slug，先用最小请求验证 |
| 连接超时 / connection refused | `base_url` 写错，或本机转发服务没起来 | 直接 curl 提供方的 responses 端点确认可达；若走本机转发，先确认端口在监听 |
| 选项里看不到第三方模型 | 目录没生效（客户端启动后才改的） | 重启客户端；确认 `model_catalog_json` 路径存在且 JSON 合法 |
| 请求发出但立刻被拒 | `wire_api` 不是 `responses`，或提供方只有 Chat Completions | 确认协议；只有 Chat Completions 的提供方需要额外的转换层 |
| 出现 service tier / 未知字段 warning | 原生专有设置被第三方模型忽略 | 属预期，可忽略；必要时在切换模式下临时去掉该设置 |
| 切回原生后仍然走第三方 | 根 `model_provider` 没删干净 | 检查根配置里 `model` / `model_provider` / `model_catalog_json` 三行 |
| 客户端行为与 CLI 不一致 | 客户端只在启动时加载配置与目录 | 退出并重开客户端后再判断 |

## 验证顺序

1. 配置能解析（只读命令）。
2. 覆盖方式的一次真实请求返回内容。
3. 根配置切换后的真实请求返回内容。
4. 重启客户端后的真实对话。

每一步都通过再进入下一步；失败时保留原始报错，再决定是改参数还是回退。
